## 1. Summary

Zoldify is a marketplace for individuals to sell second-hand and surplus goods to
other individuals, where the platform holds the buyer's payment in escrow and
releases it to the seller only after the buyer confirms the item arrived.

The distinguishing mechanism is payment custody, not catalogue. Classified-ads
platforms introduce buyer and seller and then step out of the way when money moves;
Zoldify stays in the middle of that step. See
[Problem Discovery](./2026-08-12-problem-discovery.md) for why that gap exists and
[PR/FAQ](./2026-08-12-pr-faq.md) for how it is positioned.

## 2. Goals and non-goals

### Goals

**G1. A buyer can complete a purchase without sending money to a stranger.**
Payment enters escrow, not the seller's account. This is the product.

**G2. A seller can be paid, and get the money out to a bank account.**
Escrow release → available balance → withdrawal. All three stages, end to end.

**G3. Every movement of money is reconstructable.**
Double-entry, append-only, balanced by construction. No stored balance that can
drift.

**G4. The same operation performed twice moves money once.**
Duplicate webhooks, double-clicked buttons, concurrent requests.

**G5. The product runs on web and on both mobile platforms, against a real
deployed API.** A capstone requirement, not a product one, but it is binding.

### Non-goals for v1

| Not building | Why |
|---|---|
| Ratings and reputation | Meaningful only with real traffic; adds schema and moderation surface |
| Delivery tracking integration | Requires a carrier account and partner API |
| Formal dispute-resolution workflow | The largest omission — see §7 gap 6 and PR/FAQ I8 |
| Seller identity verification (KYC) | Regulatory territory the team is not equipped for |
| Promoted listings / advertising | Revenue experiment, not core mechanism |
| Multi-currency | Single market, VND only, integer đồng |

Non-goals are listed so the defense can answer "why didn't you build X?" with a
reason rather than a silence.

## 3. Users

Two personas, defined in [Problem Discovery §4](./2026-08-12-problem-discovery.md)
and marked there as **untested assumptions**:

- **Occasional seller** — a few items a year, not a business, will not learn a
  seller console.
- **Deliberate second-hand buyer** — buying used on purpose, has backed out at the
  payment step before.

Plus one operational role:

- **Administrator** — approves listings, resolves stuck money, approves
  withdrawals.

## 4. Success metrics

Defined in [PR/FAQ §I6](./2026-08-12-pr-faq.md). Summarised: escrow release rate,
median hours from delivery to buyer confirmation, refund rate, count of escrows
holding over 14 days, repeat sellers. All five are direct database queries.

Signups and page views are explicitly **not** success metrics for this product.

## 6. Requirements

### Functional — by use case

The ten primary use cases are already enumerated for Chapter II. Their
requirements restated as acceptance conditions:

| ID | Use case | Must be true when done |
|---|---|---|
| UC-01 | Register with email OTP | Account unusable until the code is verified; codes expire; failed SMTP surfaces an error rather than silently succeeding |
| UC-02 | Log in | Wrong credentials are indistinguishable from a missing account |
| UC-03 | Post an item for sale | Condition is **declared, not defaulted**; listing enters moderation |
| UC-04 | Search and filter | Results exclude inactive and sold items |
| UC-05 | Place order and pay | Stock verified under lock; escrow per seller; duplicate webhook moves money once |
| UC-06 | Confirm delivery received | **Buyer only.** The seller cannot mark an item delivered |
| UC-07 | Release escrow to seller | Three legs — seller, platform fee, escrow — in one transaction. Partial failure moves nothing |
| UC-08 | Request a withdrawal | Money set aside at request time; a second concurrent request for the same balance fails |
| UC-09 | Approve a withdrawal | Admin only; rejection returns the money to available |
| UC-10 | Chat with a seller | Messages delivered live; history persists |

**The rule underneath UC-06 and UC-09 is worth stating explicitly, because it is
the same rule twice:** whoever gains from an action must not be the one who
performs it. The seller gains from delivery being confirmed, so the seller cannot
confirm it. This is enforced in the status-transition policy and covered by a test
sweeping all 49 status pairs.

### Non-functional

| Area | Requirement | Status |
|---|---|---|
| Money representation | Integer đồng (BIGINT). No floating point, no DECIMAL arithmetic | ✅ in ledger |
| Consistency | Every money operation is one database transaction, or it is none | ✅ |
| Idempotency | Deterministic key per operation; replay produces one transaction | ✅ |
| Concurrency | Row locks acquired in ascending id order to avoid deadlock | ✅ |
| Auditability | Balance derived from entries, never stored | ✅ — `users.balance` dropped |
| Module boundaries | Six bounded contexts; `money` must not depend on `ops` | ✅ — lint ratchet at 29 |
| Transport security | HTTPS with a valid certificate on a real domain | ❌ not deployed |
| Availability | Not specified — academic project | n/a |

### Data model constraint that the product depends on

Condition is not decoration. On a marketplace of one-off items where the buyer
cannot inspect the goods, **the declared condition is the primary piece of
information the buyer is trusting.** It must therefore be: required at listing
time, constrained to the four defined values, and never silently defaulted. It is
currently none of those three — see gaps 1 and 2.

## 7. Gap register — where the product story and the code disagree

Found by reading the code, not by inspection of documents. Each row names the file
so it can be checked rather than believed.

### Gap 1 — Condition silently defaults to `new`

In `src/catalog/products/entities/product.entity.ts`, the `condition` column is
declared `@Column({ ... default: 'new' })`. The frontend deliberately defaults to
`good` instead — `Zoldify_Frontend/src/lib/product-condition.ts`, constant
`DEFAULT_CONDITION`, states the reasoning in a comment: *used goods should default
to "good", not "new"*.

So the two halves of the system disagree, and the backend wins for anything that
does not go through the web form — the mobile app, the API, a seeded record.

**Why this matters beyond tidiness.** On a marketplace whose entire pitch is
trust, silently assigning an item the *most flattering* value the seller did not
choose is a product defect. Condition should be required, with no default at all.

**Fix:** make `condition` required in the DTO; drop the column default.

### Gap 2 — `condition` accepts any string

In `src/catalog/products/dto/create-product.dto.ts`, the `condition` field carries
`@IsOptional()` and `@IsString()`, with the four valid values written in a
**comment**. No `@IsIn`.

This is not theoretical. The frontend file above records that the database already
contains `used` and `refurbished` from an earlier build, and that a page which did
not recognise those values would overwrite the real condition on save.

**Fix:** `@IsIn(['new','like_new','good','fair'])`, plus a migration normalising
existing rows.

### Gap 3 — Seed data contradicts the product

`src/seed.ts` seeds iPhone 16 Pro Max, MacBook Pro M4, Dell XPS 16, AirPods Pro 2 —
current-model retail goods, in categories named *Điện thoại* and *Laptop*.

Selling a sealed item is legitimate on Zoldify — `new` is one of the four
conditions. The problem is that **100% of the demo data is brand-new catalogue
stock**, so anyone opening the demo sees a Shopee clone and the escrow story has
nothing to attach to.

**Fix:** reseed as a believable second-hand market — mostly `good` and `like_new`
with visible wear described in the text, one or two `new` sealed items, prices
below retail, `stock = 1`.

This is cheap and it changes what the examiner sees first.

### Gap 4 — Retail-inventory fields left over

`sold_count`, `is_freeship`, and `brand` on `products` are concepts from
merchant retail. `stock` defaulting to `1` is correct for one-off items and should
stay.

Low severity — decide per field whether to use or remove, and do not let them shape
the UI into looking like a shop.

### Gap 5 — `ProductStatus.SOLD` is declared and never assigned

`product.entity.ts` declares `SOLD = 'sold'` in the `ProductStatus` enum. **No code
anywhere sets it** — searched across `src`, the only occurrence is the declaration
itself. Re-checked after the currency migration on 12/08/2026: still unassigned.

On a marketplace of unique items this is a real behavioural bug: a sold item stays
`active`, keeps appearing in search and category listings, and buyers can open a
listing for something that no longer exists.

**Fix:** set `status = SOLD` when stock reaches zero, inside the same transaction
that decrements it, and exclude sold items from listing queries.

### Gap 6 — Escrow can be held forever

There is no scheduled job, no timer, and no expiry in the `money` or `ordering`
modules — verified 12/08/2026. If the buyer never confirms receipt, the seller is
never paid and there is no automatic way out.

**Fix:** automatic release a fixed window after delivery, with the buyer able to
open a dispute to stop the clock. Belongs in the reconciliation worker.

Fully discussed in [PR/FAQ I3](./2026-08-12-pr-faq.md). **Do not hide this at the
defense.**

### Gap 7 — The withdrawal flow has no interface  ✅ **ĐÃ ĐÓNG 13/08/2026**

> Đã dựng cả hai màn hình. Mô tả bên dưới giữ nguyên vì nó ghi lại tình trạng
> lúc phát hiện. Thiếu sót còn lại: **mobile vẫn không có màn rút tiền nào.**
> Phải mở thêm một route backend để hoàn tất: `PATCH
> /admin/withdrawals/:id/complete` — hàm service đã có và có test, chỉ thiếu
> khai báo route, nên lệnh rút đi tới `approved` là đứng lại vĩnh viễn.


The backend implements all three stages — request holds the money, reject returns
it, complete moves it out — and it is covered by nine integration tests on a real
MySQL instance, including a concurrency test proving two simultaneous requests for
the same balance cannot both succeed.

The interface does not exist. `Zoldify_Frontend/src/app/profile/wallet/page.tsx` is
243 lines and contains no reference to withdrawal. There is no `admin/withdrawals`
route. The word appears in the frontend only in generated API types and in a label
map.

**This is the most consequential gap in the document.** G2 — a seller can actually
get paid — cannot be demonstrated end to end. The flagship differentiator stops one
screen short of being real, and it stops there for want of two forms, not for want
of any hard problem.

**Fix:** a withdrawal request form on the wallet page, and an admin approval
screen. Both are ordinary CRUD against endpoints that already exist and are tested.

### Gap 8 — Rubric Level 3 items missing

OAuth sign-in, a recommendation feature, and push notifications are all required by
the grading rubric and none exist. `auth.controller.ts:108` contains only a comment
mentioning Firebase Google login.

Not product gaps — grading gaps. Recorded here so they are not lost between the
rubric and the backlog.

## 8. Release criteria

Zoldify v1 is ready to defend when:

1. A buyer can complete a purchase on the deployed site over HTTPS on the real
   domain, from browse to escrow release, and the app does the same against the
   same API.
2. A seller can request a withdrawal and an admin can approve it, in the interface,
   without touching the database. *(Đạt trên web 13/08/2026.)*
3. A sold item disappears from listings. *(Blocked by gap 5.)*
4. The demo catalogue reads as second-hand goods. *(Blocked by gap 3.)*
5. `npm test` passes and the ledger invariant `SUM(entries) = 0` holds after the
   demo script has been run.
6. Every gap in §7 that is not fixed is written into the report's limitations
   section, with the reason.

Criterion 6 is not a formality. A known limitation that is documented reads as
engineering judgement; the same limitation discovered by an examiner reads as an
oversight.
